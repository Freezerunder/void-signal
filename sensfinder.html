How the measurement actually works

The trainer turns your view by mouse pixels × DPI-derived degrees-per-count, using the browser's Pointer Lock API for relative mouse movement instead of absolute cursor position. That's the same relative-delta approach games use, just without direct access to raw HID counts.
1 browser "pixel" of movement is treated as ≈1 raw mouse count. That assumption holds well on Windows when pointer speed is left at the default 6/11 and "Enhance pointer precision" is off — the standard "raw input" setup most competitive players already use.
The Convert tab's math (yaw constants, cm/360 formula) doesn't depend on any of this — it's pure arithmetic from your DPI and cm/360, so it's exact regardless of platform. Only the feel in the Flick Trainer is affected by the roadblocks below.

Known roadblocks (browser vs. native game)

No raw HID access. Browsers can't read raw mouse-controller counts the way a game's raw input thread can — Pointer Lock gives OS-processed pixel deltas. Windows with default pointer curve settings tracks 1:1 closely; anything else introduces drift.
macOS mouse acceleration can't be fully disabled from a webpage. macOS applies its own cursor-speed curve system-wide, including in Safari/Chrome. Trackpads make this worse — they use an entirely different acceleration curve. For a closer 1:1 feel on Mac, third-party tools like Mos, SteerMouse, or LinearMouse can flatten the curve; the browser itself has no setting for this.
DPI can't be read from the OS or mouse. There's no browser API for it — it has to be typed in from your mouse's software/manual. A wrong DPI value throws off every cm/360 and converter number on this page.
Pointer Lock support varies. Chrome, Firefox and Edge support it fully; Safari on macOS supports it but has historically been less consistent about it; there's no equivalent on iOS/iPadOS/Android since there's no relative-motion mouse input there at all — this tool is desktop-mouse only.
Very fast flicks can outrun a single animation frame. The page samples getCoalescedEvents() where the browser exposes it (Chromium) to recover sub-frame mouse samples instead of only the last one per frame; Firefox/Safari don't expose that API, so very fast flicks there are averaged per-frame instead, which is slightly less precise.
Yaw constants can drift. They're the community-verified defaults for each engine at the time this was built (Aug 2026) — a developer changing the default sensitivity scaling in an update would make that one row stale until updated here.

What's next

This is the web version — it gets you a real, usable cm/360 and exact per-game numbers today. A native build (using real raw-input APIs on Windows/Mac/Linux) would remove the OS pointer-curve roadblock entirely and could read DPI straight from supported mice; that's the natural next step once this version's been road-tested.
